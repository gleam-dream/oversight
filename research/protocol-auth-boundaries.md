# Protocol and authorization boundaries

Date: 2026-09-19

## Decisions

- Relay must target the current released MCP revision `2026-07-28` first. The revision is no longer a draft: it replaced the initialize handshake and protocol sessions with self-contained requests, `server/discover`, and per-request metadata. The next compatibility target is `2025-11-25`, because the official Tier 1 assessment runs both frozen requirement sets at their own wire revisions; the proposed `Rev20260728` must therefore lose its draft label rather than be removed ([current specification](https://modelcontextprotocol.io/specification/2026-07-28), [release](https://blog.modelcontextprotocol.io/posts/2026-07-28/), [version matrix](https://plan.modelcontextprotocol.io/matrix)).
- Relay should be one Erlang-target Hex package with internal modules for protocol values, tool construction, server dispatch, client behavior, HTTP, authorization, and test support. A pure module boundary is sufficient until another package needs an independent release cadence, target, or dependency set; the proposed eight-package publication layout would impose coordination before such evidence exists.
- Warden should remain an OIDC relying-party and OAuth client library backed by `oidcc`. Relay authorization has different roles: a Relay server is an OAuth resource server, while a Relay client is an OAuth client with MCP-specific discovery, resource binding, scope accumulation, issuer migration, and callback checks. Neither package should depend on the other initially.

## Pinned evidence

- The MCP authority is the `2026-07-28` specification tag, tag commit `5f5440bb26a62e2cf3440b92da5a667efa03b267`, under MIT. Its TypeScript schema is authoritative. Relay should record this commit beside generated or translated protocol fixtures ([tag](https://github.com/modelcontextprotocol/modelcontextprotocol/tree/2026-07-28), [commit](https://github.com/modelcontextprotocol/modelcontextprotocol/commit/5f5440bb26a62e2cf3440b92da5a667efa03b267)).
- The conformance authority is `@modelcontextprotocol/conformance` `0.2.0-alpha.10`, which the frozen `requirements/2026-07-28.yaml` names as its release anchor. Current source inspected at commit `7169291ec0b68eb370fddcd9947313ab0d5e4156` reports `0.2.0-alpha.11` and is MIT; it distinguishes required scenarios from extensions, later additions, and pending tests. Relay may report conformance only from `--requirements 2026-07-28`, not from selected scenarios or an expected-failures baseline ([suite](https://github.com/modelcontextprotocol/conformance)).
- Official implementation oracles are TypeScript client/server `2.0.0` at source commit `cc4b41617ce3601b1290d67216ea0b194a3cd9ac` and Python `2.0.0` at commit `6f69a3758ebf2ee55ce050f58b470ce11af71133`. Both implement the modern revision and earlier revisions; their implementation choices remain scoped oracles because the specification and conformance suite decide wire correctness ([TypeScript roadmap](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/ROADMAP.md), [Python release](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.0.0)).
- `mcp_toolkit` `0.3.1`, commit `7085e9dd64490d06e338935b3f497b85bb82d068`, is Apache-2.0. It provides a typed server builder, generic argument decoders, protocol records, snapshots, and stdio plus older HTTP/SSE helpers, but its protocol constant is `2025-06-18`, tool schemas enter as JSON strings, and it has no official conformance integration. Relay should reuse API and test ideas, with attribution if code is copied, rather than depend on it ([source](https://github.com/mikan-laboratory/mcp_toolkit/tree/v0.3.1)).
- `mcp_client` `0.1.0`, commit `8dce5d3819bd8ac0cccadc68bb8b3773398ba38f`, is Apache-2.0. Its useful evidence is OTP ownership of child ports, stderr isolation, a one-megabyte line buffer, crash eviction, and reconnection tests; its public calls return raw `Result(String, String)`, its only transport is stdio, and it implements `2024-11-05`. Relay should port the operational cases after checking current framing rules, not inherit its API or protocol model ([source](https://github.com/manelsen/mcp_client/commit/8dce5d3819bd8ac0cccadc68bb8b3773398ba38f), [package](https://hex.pm/packages/mcp_client/0.1.0)).
- Warden should pin `oidcc` `3.9.0`: annotated tag object `e5bad400ecb538bc0d826d54516fd7ee3b1cb2a8`, source commit `aa212d52d0140addf057c34917b734647401b34e`, Apache-2.0, with OTP 27 as its minimum. Versions from `3.2.0-beta.1` through `3.8.0` accept an encrypted unsigned ID token in one path, so the draft's `3.8.0` reference is unsafe ([package](https://hex.pm/packages/oidcc/3.9.0), [advisory](https://github.com/erlef/oidcc/security/advisories/GHSA-533g-4vf3-xwrj)).
- OpenID certification applies to `oidcc` `3.0.0`, not Warden or `oidcc` `3.9.0`. The certified profiles are Basic RP, Config RP, Form Post RP, and third-party-initiated RP; the upstream harness also documents refresh and RP-initiated logout runs. These results are historical acceptance evidence, while Warden still needs wrapper and current-version conformance evidence ([certified implementations](https://openid.net/certification/certified-openid-relying-parties-profiles/), [harness](https://github.com/erlef/oidcc_conformance/tree/b632d9745b9490229ebca004b4df9928e1457d51)).

## Relay construction sequence

- The first experiment is type-only. A typed constructor must accept a name, `Codec(arguments)`, `Codec(result)`, and `fn(arguments) -> Result(result, ToolError)`, then close over those values and return one opaque non-generic registered tool. Positive fixtures place two tools with different argument and result types in one registry; negative fixtures pair a handler with the wrong codec. The public API contains no `Dynamic`; JSON erasure occurs inside the constructor.
- The first runnable slice is a modern Streamable HTTP server containing `server/discover`, `tools/list`, and `tools/call` for text success and tool error. It validates JSON-RPC, `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`, per-request metadata, body limits, media types, Origin, and Host; a framework-neutral dispatch module performs protocol work, while a Mist shell owns sockets. Selected conformance scenarios are development evidence only.
- This slice is deployable only on loopback or behind a caller-supplied verifier. Public protected deployment waits for Relay's resource-server contract, so deferring OAuth does not create an unauthenticated production claim.
- The next server slice completes every scored `2026-07-28` server requirement: content variants, resources, prompts, progress, cache fields, multi-round-trip input, header validation, DNS-rebinding protection, and required error behavior. The gate is a clean frozen requirement run with no baseline.
- The client then adds modern HTTP discovery, typed method/result pairing, cancellation, timeouts, response limits, and server-era pinning. Client authorization follows as its own vertical slice and must pass the frozen client auth requirements; stdio and `2025-11-25` handshake compatibility follow with both frozen requirement sets green.
- Tasks, Apps, DPoP, workload identity, deprecated server-initiated features, and older revisions remain later modules or extensions. A module becomes another published package only after an independent consumer proves a different dependency or release need; testkit and conformance executables remain repository tooling until then.

## Authorization ownership

- Warden owns provider configuration, login transactions, authorization redirects, callbacks, code exchange, refresh, client credentials, userinfo, logout, and optional introspection access. It must generate and store state, nonce, and PKCE verifier values; bind each transaction to provider, redirect URI, and expiry; reject replay; parse callback errors; compare state; and validate the RFC 9207 `iss` callback parameter before code exchange.
- `oidcc` owns discovery and JWKS refresh, authorization URL and PAR/JAR construction, token-endpoint authentication, code exchange, signature and configured algorithm checks, issuer, audience, expiry, not-before, supplied nonce, `azp`, `at_hash`, refresh-response subject, DPoP, and FAPI profiles. Its defaults are insufficient as a facade policy: nonce validation defaults to `any`, PKCE is not required unless requested, and its high-level exchange accepts an authorization code rather than the callback, so it cannot check state or callback `iss`.
- Relay server authorization owns RFC 9728 protected-resource metadata, `WWW-Authenticate`, bearer extraction, resource/audience binding, required scopes, and conversion of verified claims into an opaque request auth context. Its narrow verifier contract may be implemented by local JWT validation or remote introspection, but introspection is only a way to obtain token status and claims; it does not decide MCP resource, audience, scope, tenant, or tool policy.
- Relay client authorization owns protected-resource discovery, authorization-server selection and migration, CIMD or pre-registration, PKCE, resource indicators, issuer-bound credentials, incremental scopes, refresh rotation, callback state and `iss`, and bounded retry. Warden's generic login API does not replace these MCP rules. `glow_auth` and `flwr_oauth2` are request builders without OIDC discovery and token-validation evidence, so neither replaces `oidcc` or the MCP conformance-driven client flow ([glow_auth](https://glow-auth.hexdocs.pm/), [flwr_oauth2](https://hex.pm/packages/flwr_oauth2)).

## Warden FFI and validation

- Warden should use exact `oidcc = "3.9.0"` resolution with a committed lockfile. One Erlang boundary module constructs option maps and TLS terms, calls the pinned functions, flattens records into tagged maps, and catches foreign exceptions; Gleam decoders reject every unexpected shape. The boundary must never create atoms from request data, stringify unknown backend terms that may contain secrets, or treat an unmapped error as success.
- Warden should expose typed errors for invalid or expired transaction, state mismatch, issuer mismatch, replay, provider not ready, transport failure, token rejection, malformed backend response, unmapped backend error, and foreign exception. Contract tests cover each wrapper branch; differential tests call raw `oidcc` and Warden against the same fixtures; upstream fixtures and certification scenarios retain provenance and license notices.
- Version 1 should accept only configured HTTPS issuers, pass explicit peer verification, system trust anchors, hostname checking, and bounded timeout through `request_opts`, and keep tokens and keys opaque and redacted. `oidcc` exposes a custom HTTP-adapter behavior, but its default adapter buffers the response and does not itself establish a body-size or SSRF policy.

## Bounded remaining experiment

- Before Warden's production release, implement one malicious-provider harness against the exact `3.9.0` HTTP-adapter seam. It must exercise a private-address endpoint, DNS rebinding, cross-host redirect, oversized fixed and chunked bodies, timeout, invalid certificate, unknown key refresh, and malformed adapter return. If the adapter cannot reject before connection and before body allocation, Warden must ship a bounded custom adapter or perform discovery and JWKS retrieval outside `oidcc`; this result can change the FFI size and HTTP ownership, but not the decision to reuse `oidcc` for RP token and JOSE behavior.
